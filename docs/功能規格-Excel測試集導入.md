# Excel 測試集導入 功能規格 v1.0

狀態：待確認 | 撰寫：Vera（產品） | 日期：2026-10-31
對應需求文檔：FR-47～FR-49（V1.0 範圍內，P0）
涉及的界面語言：沿用皮膚規範 v1.3「Linear 淺色」，不新增視覺樣式。

---

## 1. 一句話

平台提供一份標準 Excel 模板，使用者下載、填好、一鍵導入，導入完就能直接選 Agent 跑，跑完出報告——不需要懂 JSON、不需要逐條在界面裡敲。

## 2. 為什麼要做

目前建測試集只能在界面一條一條加案例，或匯入 CSV／JSON。前者在 20 條以上就不現實；後者要使用者自己拼 JSON 結構，業務同事做不到。Excel 是業務同事手上現成的工具，也是唯一能讓「非開發」把案例交出來的格式。

這條路打通後，真正的瓶頸才從「輸入案例」變成「案例寫得好不好」。

## 3. 模板設計

檔案：`.xlsx`（不接受 CSV 代替；Excel 另存 CSV 會掉下拉與說明頁）。

### Sheet 1「案例」

| 欄 | 名稱 | 必填 | 說明 |
| --- | --- | --- | --- |
| A | 案例名稱 | 是 | ≤100 字，同批內不可重複 |
| B | 案例類型 | 是 | 下拉八選一：基礎問答／指令遵循／知識庫問答／工具調用／多輪對話／複雜任務／異常處理／安全性 |
| C | 輸入 | 是 | ≤2000 字，可含換行 |
| D | 預期結果 | 否 | ≤2000 字，人工評分時的參考答案 |
| E | 判定方式 | 是 | 下拉：必須包含／不能包含／不超過字數／必須在幾秒內回應／必須拒絕／AI 依標準評分／由開發預配。可多選（例如「必須包含＋不能包含」），以逗號分隔 |
| F | 判定內容（選填） | 條件必填 | 依 E 填對應值：要包含的詞、不能包含的詞、字數上限、毫秒上限。選「由開發預配」時留空，由開發另附規則。**預設留空由平台依 E 自動生成，產品經理不需要寫 JSON** |
| G | Rubric | 條件必填 | E 含「Rubric」時必填；≤1000 字 |
| H | 逾時（毫秒） | 否 | 預設 10000；允許 1000–120000 |
| I | 優先級 | 否 | 下拉：高／中／低，預設中 |
| J | 讀寫類型 | 否 | 下拉：讀取／寫入，預設讀取 |
| K | 多輪腳本（JSON） | 否 | 有值則視為多輪案例，格式 `[{"input":"…","expected":"…"}]`，最多 10 輪；填了此欄則忽略 C |
| L | 備註 | 否 | ≤500 字，不參與評測 |

### Sheet 2「填寫說明」

- 欄位定義表（與上表一致）
- 枚舉值清單（案例類型八個、判定方式六個、優先級三個、讀寫兩個）
- 判定內容的三個填寫範例（正確一條、缺值一條、格式不對一條）
- 模板版本號：`template_version = 1`（單獨一格，導入時檢查）

### 下載提供兩個選項

1. **空白模板**：只有表頭、說明頁與下拉，無案例。
2. **標準範例集**：八類各 2 條，共 16 條，可直接跑通一次端到端，也可作為改寫起點。範例集是起點不是權威，正式使用要換成業務真實案例。

> 待確認：這 16 條範例由我先擬，還是等業務提供真實案例後替換？（建議先擬，能讓使用者第一次下載就看到完整結構）

## 3.1 五種判定方式與底層規則的映射（給開發，照這張實作校驗）

介面只給五種業務語言判定；底下對應 `scoring.ts` 現有的七種規則。**不允許出現「導入時能選、跑的時候沒人實現」。**

| # | 判定方式（界面／模板） | 底層實作 | 現況 | 動作 |
| --- | --- | --- | --- | --- |
| 1 | 必須包含這些詞 | `contains`（多詞全部命中） | 已有 | 直接用；多詞以逗號分隔 |
| 2 | 不能包含這些詞 | `contains` 加否定 → 需新增 `not_contains`（或 `contains` + `negate:true`） | **沒有** | 必須補。附錄 A 第 14、15 條就用到，不補則那兩條無法實作 |
| 3 | 不超過 N 字 | `max_length` | 已有 | 直接用；中文字以字元計 |
| 4 | 必須在 N 毫秒內回應 | `max_latency_ms` | 已有 | 直接用；界面以秒顯示、存毫秒 |
| 5 | 必須拒絕（不能照做） | 複合：內建拒絕語詞表（無法提供／不能提供／恕難…）＋ 內建敏感內容詞表（密碼、身分證、電話…） | **沒有** | 必須補。做成一個 `refuse` 複合檢查，兩組詞表由平台維護，PM 只選這一項 |
| — | （不給 PM）`equals` | 併入 #1 的「整句完全相同」子選項 | 已有 | 低優先，可先不做 |
| — | （不給 PM）`regex` | 留給開發預配 | 已有 | 只在「由開發預配」路徑使用 |
| — | （不給 PM）`jsonpath_exists` | 留給開發預配（需知道回應結構） | 已有 | 同上 |
| — | （不給 PM）`tool_called` | 工具調用類案例由平台自動附加，PM 不選 | 已有 | 取不到結構化記錄時記「無法判斷」，不當 0 分 |

覆蓋檢查：五種判定覆蓋了 `contains`、`max_length`、`max_latency_ms`，新增 `not_contains`、`refuse` 兩個實作，`equals` 併入 #1；`regex`、`jsonpath_exists`、`tool_called` 明確不給 PM，走開發預配或平台自動。八類規則全部有歸屬，沒有孤兒。

## 3.2 判定方式要逐條記錄並在報告裡露出

- 每條用例的判定方式與判定內容必須存進案例（隨測試集版本固化），不得只存在 Excel 裡。
- 報告與明細顯示的是業務語言，例如「判定：必須包含『退款政策』、『7 天內』」，**不得顯示 JSON**。
- 由開發預配的複雜規則，界面顯示唯讀一句話摘要（例：「需符合開發預設的格式規則（三段式編號）」），仍然不出現 JSON。
- 產品經理要能回答「這條為什麼算過」，不需要找人查規則。

## 3.3 報告裡的「無法判斷」寫法（不出現 N/A）

- 所有原本顯示 N/A 的位置，改成業務語言：「這項無法判斷」，並在同一行給原因。
- 報告頂部彙總一句，例：「本批有 2 項無法判斷：測試集沒有覆蓋工具類用例。」
- 原因只能是這五種，用固定話術：測試集沒覆蓋／Agent 沒有提供這項紀錄／這項被平台攔下沒送出／樣本太少不作判斷／還沒跑。
- 不得出現 `N/A`、`null`、`undefined` 或英文代碼。

## 3.4 分享連結（P1，依定位恢復）

定位要求「報告能直接發出去」，因此分享連結列為 P1。約束四條，缺一不做：

1. **只讀**：只能看報告，不能進任何可編輯頁面。
2. **有有效期**：預設 7 天，可選 1／7／30 天，過期即失效。
3. **可撤銷且立即生效**：撤銷後舊連結立刻打不開，不需要等快取過期。
4. **不含憑證與內部 ID**：連結不得帶 API Key、內部資料庫 ID、Agent 端點位址；報告內也不顯示這些。

這是對外發的東西，出事比內部頁面嚴重：寧可少做，不可做鬆。

## 4. 導入規則

### 4.1 前置校驗（整檔）

- 檔案 ≤5MB、≤500 行；超過直接拒絕並說明上限。
- 必須是平台產生的模板：檢查 Sheet 名稱、表頭順序、`template_version`。任一不符 → 拒絕並提示「模板版本不符，請重新下載」。
- 單元格以 `=` 開頭一律當純文字處理（防公式注入），不做求值。

### 4.2 逐行校驗

七類錯誤，逐行回報行號與具體原因：

| 錯誤 | 訊息示例 |
| --- | --- |
| 必填缺失 | 第 7 行：案例名稱為必填 |
| 枚舉不認識 | 第 9 行：案例類型「安全」不在允許值內（可選：基礎問答／指令遵循／知識庫問答／工具調用／多輪對話／複雜任務／異常處理／安全性） |
| 條件必填缺失 | 第 11 行：判定方式選了「必須包含」，但判定內容為空 |
| 判定內容格式不對 | 第 12 行：「不超過字數」需填正整數，目前是「二十」 |
| 判定方式不認識 | 第 12 行：判定方式「看情況」不在允許值內 |
| 數值越界 | 第 14 行：逾時 500000 超出 1000–120000 |
| 批內重名 | 第 15 行：案例名稱與第 6 行重複 |

### 4.3 寫入策略：整批或全不（all-or-nothing）

有任何一行不通過，整批不寫入，回報完整錯誤清單，使用者改完重導。

**這是刻意不採「逐行部分成功」**：Excel 是整批作業，一次幾十上百條，半套資料比沒有更難收拾——使用者改完重導時分不清哪些進了、哪些沒進，重複名稱還會擋住自己。逐行導入只適合小批量補資料，與此場景不同。

不做「僅導入通過的行」開關（已定），保持單一邏輯：要嘛全進，要嘛全不進。

### 4.4 導入目標

- 只做「新建測試集草稿」，名稱取檔名（去掉副檔名），可改。
- 追加到既有測試集草稿的模式 V1.0 不做（會與版本不可變、重名校驗糾纏，且目前無此需求）。
- **已發佈版本不可變**：導入只產生草稿，需按「發佈」才形成新版本；已發佈版本不受影響。

### 4.5 導出（與導入同一模板格式）

- 測試集詳情提供「導出 Excel」，輸出當前草稿或指定版本的案例，欄位與模板 A–L 完全一致，可直接再導入。
- 用途：備份、跨環境搬移、以及驗收第 6 條的 round-trip。
- 導出檔案同樣帶 `template_version`，導入時走同一套校驗。

## 5. 導入後一鍵執行

導入成功頁顯示：`已導入 N 條案例（草稿）` + 一個主按鈕「發佈並執行」。

按下後依序：

1. 發佈測試集新版本（若已有草稿未發佈的變更，一併發佈）。
2. 選 Agent 版本（下拉，列出所有可用 Agent 版本；無可用時引導去接入）。
3. 設定重複次數 N（預設 1）與並發數。
4. 建立實驗（四元組：Agent 版本 + 測試集版本 + 評分規則集版本 + N）。
5. 啟動批量執行，進度在實驗詳情可見。
6. 完成後自動跳到報告頁。

任一步失敗就停在該步並說明原因，不自動略過。

## 6. 驗收（8 條）

1. 下載空白模板與標準範例集，Excel 開啟後表頭、說明頁、下拉、版本號皆正確。
2. 用標準範例集導入 16 條，全部成功，生成草稿測試集，案例數與類型分佈與檔案一致。
3. 製造五類錯誤（缺必填、枚舉錯誤、判定內容格式不對、逾時越界、批內重名），整批不寫入，逐行回報行號與原因。
4. 手動刪掉一列表頭或改版本號 → 拒絕導入並提示重新下載。
5. 導入成功頁按「發佈並執行」，選 Agent 後跑完並自動跳到報告，報告內案例數與導入數一致。
6. 導入 → 導出 Excel → 再導入，案例內容一致（round-trip 無損）。
7. 超過 500 行或 5MB → 拒絕並說明上限。
8. 單元格填 `=1+1` → 存為文字「=1+1」，不求值。

## 7. 給開發的實作要點

- 用 `exceljs`（可產生帶 data validation 與樣式的 xlsx，也可讀取）。不要用 SheetJS 社群版產模板，樣式與下拉支援不足。
- 模板由後端生成（同一份程式產出空白版與範例版），保證下載與導入校驗用的是同一套定義，避免欄位順序漂移。
- 模板版本號單獨存一格並在程式裡有常數；改欄位就升版本，導入時比對，舊版提示重新下載。
- 解析在後端完成，逐行校驗後再一次寫入（交易包裹），錯誤清單結構化回傳（行號、欄位、原因）。
- 別把上傳檔案落到可執行路徑；解析完即刪。
- 既有 CSV／JSON 導入**不在這次範圍**（代碼中並不存在，僅有整批覆蓋 `PUT /api/test-sets/:id/cases`）。Excel 導入與案例校驗共用同一套 `validateCases()`；CSV／JSON 導入另立項。
