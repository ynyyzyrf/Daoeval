# Agent 接入檢查清單（V1.0）

用途：接 Oumi／Dify／自定義 HTTP Agent 時逐項打勾。**任何一步對不上就停下來，把原始回應貼給產品，不要自己猜路徑。**

平台位址：`http://127.0.0.1:5280`

## 0. 前置資料

- [ ] 完整端點 URL（不是主網域）
- [ ] 認證方式：Bearer／API Key Header／自訂 Header
- [ ] 憑證（只寫不讀，存檔後只顯示末四位）
- [ ] 平台專屬參數：Oumi 需要 `groupId`（group 形態）
- [ ] 這個 Agent 是否允許寫入？預設只讀，write 類案例會被攔截、不發請求

Oumi 已知：入口 `POST /api/v1/groups/{groupId}/message:send`，另有 `tasks/{id}`、`message:stream`；swagger 沒有 request／response schema，路徑以實測為準。

## 1. 建立 Agent（`/agents/new`）

- [ ] 平台類型選對（Oumi／Dify 會預填映射模板，模板是佔位）
- [ ] 名稱、API 地址、認證方式填完
- [ ] 寫入權限與實際部署一致

## 2. 驗證連線（第三步「發送測試請求」）

- [ ] HTTP 200，驗證通過，延遲有數值
- [ ] 「回應摘要」能看到對方原始回應

失敗時訊息會指到下一步該改哪裡：

| 訊息 | 分類 | 先去改 |
| --- | --- | --- |
| 認證失敗（HTTP 401／403） | `auth_failed` | 認證方式、Header 名稱、憑證是否有效 |
| 端點不存在（HTTP 404） | `not_found` | API 地址、路徑、請求方法 |
| 被限流（HTTP 429） | `rate_limited` | 降低並發、稍後重試 |
| 回應不是合法 JSON | `parse_failed` | 端點是否回 HTML 或純文字、是否需要不同 Accept |
| 最終回答路徑「X」取不到（附回應頂層欄位） | `mapping_failed` | 按訊息列的頂層欄位改 mapping |
| 請求逾時 | `timeout` | 端點反應時間、逾時設定 |

## 3. 五個映射欄位逐項對照

在第三步的「映射解析結果」表逐行看，狀態只有四種：已取得／明確為空／取不到（null）／未配置。

- [ ] **output（最終回答）**：必填。已取得且內容合理。
- [ ] **status（執行狀態）**：可空。取不到不影響，但對方回 `failed` 時會被判失敗。
- [ ] **tool_calls（工具調用）**：三態要分清——有值＝已取得；`[]`＝明確沒有調用；取不到＝null（該維度 N/A，不當 0 分）。
- [ ] **trace**：取不到就顯示不可取得，不影響評分。
- [ ] **usage**：prompt／completion／total 三條路徑。缺哪個報表標「未提供」，不要留白也不要補 0。

Oumi 模板（`RESPONSE_MAP_TEMPLATES.oumi`）：`data.message.content` / `data.status` / `data.tool_calls` / `data.trace` / `data.usage.{prompt,completion,total}_tokens`。Dify chat-messages 與 workflows/run 是兩套路徑，模板已分開，選平台即預填。

- [ ] 若實際回應與模板不同：記下實際路徑，改 mapping 值，不動程式；之後把差異回報產品，更新模板。

## 4. 跑一條案例

- [ ] 測試集加一條 read 案例（輸入、預期、Rubric 或規則至少一項），發佈成版本
- [ ] 建實驗（N=1），跑單條或批量
- [ ] 報告頁檢查：
  - [ ] 三態證據（工具／Trace／Token）
  - [ ] 耗時
  - [ ] 失敗或攔截案例的中文分類
  - [ ] N/A 原因不是「Agent 不行」而是可解釋的原因

## 5. 對照原始回應

- [ ] 接入第三步的「回應摘要」留底
- [ ] mapping 與實際回應不一致時，原始回應（去識別化）附在回報裡
- [ ] 確認憑證沒有出現在回應摘要、日誌或導出件

## 完成標準

五個映射欄位都有明確結論（已取得／明確為空／取不到），跑一條案例能看到三態、耗時與評分，才算接完。任一步卡住就停在該步，不要用猜的路徑繼續往下跑。
