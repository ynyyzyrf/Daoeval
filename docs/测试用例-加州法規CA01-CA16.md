## 三、評分方式：7 條帶規則，9 條只有 Rubric

**只有 Rubric 的案例，Daoeval 目前給不出分**——`scoring.ts:143-151` 在沒有 `rule` 時直接回 `passed: null`，聚合時整條落到 `no_scoring_basis`。這是交接文檔列的未完成項 FR-18（AI 評分／人工複核），不是這次導入的問題。

所以我把「答案裡有硬錨點」的案例加了規則，其餘的只留 Rubric：

| 案例 | 規則 | 錨點 |
| --- | --- | --- |
| CA01 | `contains: 220` | 加班費合計金額 |
| CA02 | `contains: 320` | 三段工資合計 |
| CA05 | `regex: 40\s*(小時\|hours\|hrs)` | 年上限 40 小時 |
| CA07 | `regex: 72` | 72 小時通知界線 |
| CA08 | `regex: 1,?250` | CFRA 工時門檻（帶或不帶千分位都命中） |
| CA10 | `regex: 16600` | §16600 條號 |
| CA11 | `regex: ABC` | ABC Test |
| CA16 | 兩條 `regex` | ①必須提到上傳／未收到；②不得出現「第 N 頁」 |

CA03、CA04、CA06、CA09、CA12、CA13、CA14、CA15 只有 Rubric。

**為什麼另外 9 條不硬給規則**：這些題的答案是一段論述，用關鍵字判正誤會製造假通過——例如 CA06 只要答案裡出現「不可以」就能過，哪怕它說「不可以等發薪日，要等下個月」。假通過比 N/A 危險得多：N/A 至少看得出來「這條沒判」，假通過會被當成真的過了。

**CA16 的規則是驗過才寫的**：

```
PASS  正確回答（說明未收到、請上傳、給清單）        → 兩條都過
FAIL  虛構回答（第 12 頁、第 8 頁）                → 兩條都不過
FAIL  半虛構（承認沒收到，但又編「第 3 頁」）       → 第二條擋下
```

第二條是負向前瞻 `^(?![\s\S]*第\s*\d+\s*頁)[\s\S]*$`，專門擋「宣稱沒收到檔案卻又給出頁碼」這種最典型的幻覺。它只擋頁碼這一種，其他虛構形式仍要靠 Rubric。

## 五、首輪執行結果（2026-10-31 16:40–16:51）

實驗 `exp_EXAMPLE`、執行 `run_EXAMPLE`，對象「Oumi 專家組（真實）」v2（`av_EXAMPLE`），N=1、並發 2。

| 結果 | 條數 | 明細 |
| --- | --- | --- |
| 成功且規則通過 | 3 | CA01（$220，7s）、CA02（$320，11s）、CA16（拒絕虛構，14s） |
| 逾時失敗 | 13 | CA03–CA15，全部卡在 60 秒 |

指標頁顯示：正確性 13%（2/15）、任務能力 100%（1/1）、單次成功率 19%。

### 逾時的真正原因

不是 Agent 不會答，是**它在 60 秒內沒答完**。逾時那一刻會話的 `status` 還是 0（未完成），可見的內容只到 `router` 那一輪：*「這事關加州勞動法與合規，我請 JOHN AI 分身的法務合規視角來判斷……正在安排 JOHN AI分身 去做。」*

對照成功的那條，會話結構是三輪：

```
turn 1  main                router       「稍等，正在安排 JOHN AI分身 去做。」
turn 2  05f35ff5-b44d-…     domain-expert 由子 agent 給出法規答案
turn 3  main                synthesizer   彙整成最終回答
```

**所以這是「多輪路由 + 子 agent 研究」的耗時問題，不是連線問題，也不是權限問題**（子 agent 是能正常回覆的，CA01/CA02/CA16 都走了完整三輪）。法規細節題（用餐時間、病假、離職工資、競業禁止）要子 agent 做更多查證，單是 router 一輪就吃掉 15 秒，剩給子 agent 的不足 45 秒。

### 平台的兩個問題

1. **60 秒對這種 Group 形態不夠**。本測試集的案例逾時我原本給 60000，實測要放寬到 180000 才有意義（已發佈版本不可變，重跑要發新版本）。
2. **逾時被當成「未通過」計入分母，口徑會誤導**。13% 這個數字會被讀成「Agent 很差」，實際是「15 條裡 13 條沒跑完」。`scoring.ts:135-142` 把 `status='failed'` 直接判 `passed:false`，與「答錯」混在一起。建議報告在指標旁按失敗原因分開顯示，或讓逾時維持 N/A。

### 下一次重跑要改的參數

- 案例 `timeoutMs`：60000 → 180000（發新版本）
- 併發：2 → 1（Group 內部本來就是序列路由，外部再併發只會互相搶時限）
- 其餘不動
