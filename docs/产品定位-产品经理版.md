# 產品定位：產品經理友好的 Agent 評測系統

狀態：已定（依 2026-10-31 用戶明確定調） | 撰寫：Vera（產品）
適用範圍：本文件是這個產品的**定位基準**。之後任何功能取捨、界面文案、報告版式，與本文件衝突時以本文件為準。

---

## 1. 一句話定位與目標用戶

**一句話**：把測試集整理成 Excel，跑一次，告訴你「這版 Agent 能不能上線、比上一版好在哪」。

不是「Agent 開發調試工具」，是**上線前的評測與驗收工具**。

### 誰用

| 角色 | 在這件事裡做什麼 | 用平台做什麼 |
| --- | --- | --- |
| 產品經理 | 定義這版要達到什麼、決定能不能上 | 導入測試集、跑一次、看結論、發報告 |
| 業務負責人 | 提出業務場景與驗收標準 | 看報告、確認關鍵案例是否答對 |
| 驗收方（甲方／上級） | 判斷是否驗收通過 | 只看結論頁與退步清單 |

### 他們不懂、也不需要懂

- 不會寫 YAML，不知道什麼是 assertion 類型
- 不關心 provider、temperature、embedding、span 這些參數
- 不會去看 trace 的一層層調用，也不需要知道 Agent 內部怎麼調度
- 不想為了跑一次評測去配 CI、裝 CLI、改設定檔

### 他們真正要回答的三個問題

1. 這版能不能上線？（要一個結論，不要一堆表格）
2. 比上一版好在哪、差在哪？（要差異，不要絕對值）
3. 有哪幾條是「不能忍」的？（要點名，不要平均分）

> 判準：如果一個功能不能幫使用者回答上面三題之一，它就是「可有可無」，排在有助於這三題的功能之後。

## 2. 與 promptfoo 的分界

| | promptfoo（及同類） | 我們 |
| --- | --- | --- |
| 主要用戶 | 開發者 | 產品經理、業務、驗收方 |
| 使用方式 | 寫 YAML、跑 CLI、接 CI | 下載 Excel、填完上傳、點一次跑 |
| 產出 | 每條案例的斷言結果與 diff | 一句「能不能上線」＋證據 |
| 迴圈 | 逐條調試、改 prompt、再跑 | 一版跑一次，比上一版 |
| 成功標準 | 開發看得懂、能進 pipeline | 業務看得懂、能直接發給老闆 |

**我們不做**（明確劃出，避免又長回開發者工具）：

- CLI 與命令列工作流
- 以設定檔（YAML／JSON）定義評測
- CI／CD 集成、回歸門檻自動攔截
- Prompt 調試器、逐字比對、單條快速迭代
- 分散式 trace／span 檢視與延遲剖析

需要 CI 回歸的團隊，應該接 promptfoo 那類工具；我們的價值是「決策」而不是「調試」。兩者可以並存：開發用他們的工具調試，上線前用我們的平台做一次評測與驗收。

## 3. 由此改變的界面與文案規則

### 3.1 術語表

**對外只出現這些詞**：測試集、用例、跑一次、通過率、比上一版、能不能上線、退步、樣本量。

**禁止出現在界面的詞**（出現在任何使用者可見位置即視為缺陷）：

`assertion`、`provider`、`run_task`、`trace`、`span`、`embedding`、`temperature`、`DSL`、`JSON schema`、`token`（改說「用量」）、`N/A`（改說「這項測不了」）。

技術詞只能出現在：日誌、開發除錯頁、匯出 JSON 的內部欄位。使用者介面一律用業務語言。

### 3.2 失敗原因用業務語言

| 技術分類 | 界面顯示 | 旁邊必須有 |
| --- | --- | --- |
| `rule_miss` | 回答沒提到關鍵資訊 | 期望關鍵詞 vs 實際回答原文 |
| `wrong_answer` | 答非所問 | 問題、期望、實際三段並排 |
| `timeout` | 超時沒回應 | 等了多久、上限多少 |
| `blocked_readonly` | 權限被拒，沒有送出 | 說明是平台攔下的，不是 Agent 的錯 |
| `auth_failed` | 連不上（認證問題） | 提示去找開發確認金鑰 |
| `mapping_failed` | 系統看不懂回應格式 | 說明要請開發調整，不是 Agent 的問題 |

原則：**每一條失敗，都要讓 PM 一眼看出「是 Agent 的問題，還是平台／設定的問題」**。這兩者混在一起，報告就沒有決策價值。

### 3.3 結果頁：結論先行

現在的實現是先擺指標表，結論要人自己算。改成三段式：

1. **結論句**（最大字）：一句話講清楚這批能不能用，例如「15 條用例通過 12 條，可以上線，但有 1 條退步需要確認」／「通過率 62%，不建議上線」。
2. **三個數字**：通過率、樣本量與可信度（信賴區間）、與上一版的差異。
3. **證據**：失敗與退步的具體用例（預設展開前 5 條），再往下才是完整表格與明細。

技術細節（凍結配置、trace、耗時分布）折疊在「更多」裡，預設不展開。

### 3.4 報告要能直接發出去

匯出件（PDF／HTML）的第一頁必須自足：換一個人拿到檔案、不看平台，也能知道結論。

必須包含：結論句、樣本量與信賴區間、測試集名稱與版本、被測 Agent 與版本、哪幾條退步或沒通過（含原文對照）、產出時間。

不需要包含：配置雜湊、trace、內部 ID（可放附錄最後）。

分享連結（讓沒帳號的人看報告）屬於 PM 友好的核心能力，V1.0 先前因脫敏範圍未定而砍掉，現在依定位**恢復為 P1**，脫敏規則另行定義。

## 4. 對現有功能的重排判斷

### 4.1 符合定位，應該做（按優先序）

| 序 | 功能 | 理由 |
| --- | --- | --- |
| 1 | Excel 測試集導入／導出 | PM 唯一會用的輸入方式，決定這產品能不能被業務用起來 |
| 2 | 一鍵跑（導入→發佈→跑→報告） | 把四步合成一步，PM 不必理解四元組與版本 |
| 3 | 結論先行的結果頁 | 直接對應「能不能上線」這題 |
| 4 | 失敗原因業務化 | 對應「哪幾條不能忍」 |
| 5 | 可發出去的報告（含分享連結） | 決策要能傳遞，否則平台只是自己看 |
| 6 | 與上一版對比（A/B） | 對應「好在哪、差在哪」 |
| 7 | 按場景可選的範例測試集 | 讓 PM 不必從零寫用例；先做客服問答、知識庫問答、工具型助手三套 |

### 4.2 開發者向，砍或後置

| 功能 | 判斷 | 說明 |
| --- | --- | --- |
| 自定義評分規則 DSL 與規則 JSON 編輯器 | **砍（界面）** | 見第 5 節，這是目前最背離定位的一項 |
| 斷言（assertion）編輯器 | 砍 | 用「判定方式」下拉取代 |
| Trace／span 檢視 | 後置 | 收進「更多」，預設不顯示；PM 不看 |
| CI／CLI／設定檔評測 | 不做 | 交給 promptfoo 那類工具 |
| 接入的欄位路徑映射（mapping） | 保留但移出主流程 | 由開發一次性配置，PM 不需要看到 |
| 審計日誌 | 保留但隱藏 | 合規需要，不進主導航 |

### 4.3 一句話排序

先讓 PM 能「導入 → 跑 → 看懂 → 發出去」，四步都順了再談其它；任何不能縮短這四步的功能，排後面。

## 5. 現有功能裡最不該做的一項

**自定義評分規則 DSL 與規則 JSON 編輯器。**

理由：它把「怎麼判分」變成 PM 的日常工作，而 PM 既寫不出、也不該寫。一旦界面上有一格叫「規則（JSON）」，使用者就會被要求懂結構、懂運算子、懂轉義，產品立刻退回開發者工具；更糟的是，它同時定義了分數口徑——寫錯規則不會報錯，只會讓報告安靜地給出錯誤結論。

替代做法：界面只給「判定方式」下拉——回答包含這些詞／不包含這些詞／不超過字數／必須在幾秒內回應／必須拒絕這個請求。這五種覆蓋八成用例。真的需要複雜判定時，由開發在導入模板時一次配好，不在界面開放編輯。

（Excel 模板的「規則(JSON)」欄位同屬此類，應降級為「選填，預設由平台依判定方式自動生成」，而不是要 PM 手寫。）

## 6. 驗收：陌生人能否自己走完

由一個沒參與過本專案的人，不看說明、不找人問，完成以下五步，即通過：

1. 從首頁找到「下載模板」，下載後用 Excel 打開，知道每一欄填什麼（說明頁存在且看得懂）。
2. 填 5 條用例（或直接用範例集），上傳導入，看到「已導入 5 條」。
3. 按「發佈並跑一次」，選一個 Agent，等它跑完（進度看得懂，不需要知道什麼是四元組）。
4. 打開結果頁，30 秒內說出：「這批能不能用、哪幾條沒過、為什麼沒過」。
5. 導出報告（或拿分享連結）發給別人，對方不看平台也能讀懂結論。

任何一步需要「問一下技術同事」或「看文件才知道」，即該步不通過。

---

**一句話總結這份定位**：我們賣的是「上線前的那一次判斷」，不是「開發過程中的每一次調試」。
