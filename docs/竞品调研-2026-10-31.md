# Daoeval 競品與替代方案調研（GitHub 開源）

狀態：已完成 | 撰寫：Sage（研究） | 日期：2026-10-31 | 對應：Daoeval V1.0（通用 AI Agent 評測與優化平台）

---

## 0. 摘要

1. **同類項目很多，但沒有一個把 Daoeval 的四元組凍結當成產品核心。** 最接近的是 promptfoo（接入＋執行＋規則斷言＋CI＋Web 檢視）與 Arize Phoenix（版本化資料集＋實驗＋評分器＋自架 UI），兩者都在「跑得起來、看得見」這一層和我們高度重合。
2. **「啟動前凍結、缺一不得啟動」這種審計級語義，在 42 個受檢項目裡沒有找到等價實作。** Phoenix 有 versioned datasets、MLflow 有 experiment＋dataset、Inspect 會把 task 版本與模型寫進 log，但都是「事後可追溯」，不是「事前不可啟動」。
3. **append-only＋DB 觸發器強制不可變，也未見等價物。** 提示詞與資料集的版本化很普遍（Langfuse prompts、Phoenix datasets、MLflow registry），但「只能停用、不能改不能刪、由資料庫觸發器兜底」沒有找到公開說明。
4. **三態證據（present／none／unavailable）與 N/A 不進分母，是「統計語義」層的真差異，不是資料模型層的新東西。** promptfoo 區分 fail 與 error，多數平台用 null／skip 表示缺值；「六類原因碼＋報告頂部匯總」未見等價。
5. **規則評分不是差異，是同行做法。** promptfoo 的斷言庫（equals／contains／regex／JSON／JS／latency／cost／assert-set 閾值）幾乎一對一覆蓋我們的八類規則，接入層的「請求模板＋響應映射」也已有同構實作。這兩塊是「可以不用自己造」的首選。

## 2. 全景：五大類同類項目

| 類別 | 代表項目 | 對 Daoeval 的意義 |
|---|---|---|
| 評測編排框架（CLI／函式庫） | promptfoo、DeepEval、Inspect AI、OpenAI Evals、Tolokaforge | 直接替代「執行＋評分」層，是重合度最高的一類 |
| 平台型（實驗管理＋UI＋自架） | Phoenix、Langfuse、Opik、LangWatch、Future AGI、Braintrust、MLflow、TruLens、Agenta | 替代「測試集＋實驗＋報告 UI」層，也是我們最像的產品形態 |

| 模型評測基準 | OpenCompass、lm-evaluation-harness、lighteval、HELM、EvalScope、EvalPlus | 只評模型不評 Agent，與我們鏈路重疊少 |
| 可觀測／追蹤附帶評測 | Weave、Laminar、Helicone、AgentOps、RagaAI Catalyst、Evidently | 追蹤是它們的主業、評測是附加；是「追蹤層」的替代品，不是完整競品 |

## 6. 逐項要點（只寫與 Daoeval 決策有關的）

### promptfoo：重合度最高，接入與斷言幾乎同構
- 官方定位是「評估與紅隊的開源 CLI 與函式庫」，主打 test-driven LLM 開發，可用於 CLI、library、CI/CD（[文件](https://www.promptfoo.dev/docs/intro/)）。
- **HTTP 供應商與我們的適配器是同一種設計**：把 provider id 設成 URL，就能用 `url／method／headers／body／transformResponse` 組請求與取回應欄位（[HTTP API 文件](https://www.promptfoo.dev/docs/providers/http/)）。我們「請求模板＋響應映射路徑」等於它的子集。
- 斷言型別覆蓋 `equals／contains／icontains／regex／is-json／contains-json／javascript／python`，另有 `latency／cost` 閾值與 `assert-set` 加權（[Assertions 文件](https://www.promptfoo.dev/docs/configuration/expected-outputs/)）。我們的等值、包含、正則、JSONPath、長度、耗時、工具呼叫七類，它幾乎全有。
- Web 檢視器可自架（`apiBaseUrl` 指到自家 server），有 pass rate、逐斷言分數、篩選與分享連結（[Web UI 文件](https://www.promptfoo.dev/docs/usage/web-ui/)）。
- **沒有**：資料集版本凍結、N/A 三態、Wilson 區間、實驗級快照。它的可重現性靠「設定即程式碼＋git」。

### Arize Phoenix：最接近「平台形態」的對手
- README 明示提供 **versioned datasets**、Experiments、LLM 評測、Playground、提示詞版本管理，並可用 Docker 自架（[倉庫](https://github.com/Arize-ai/phoenix)、[資料集與實驗文件](https://arize.com/docs/phoenix/datasets-and-experiments/overview-datasets)）。
- 實驗綁定資料集，資料集可掛「dataset evaluators」，跑實驗時自動評分——這就是「測試集＋評分規則」的產品化版本。
- **差距**：它是「事後可追溯」，不是「事前凍結」；沒有「缺一不得啟動」的閘門，也沒有把案例內容／閾值快照進實驗。授權是 Elastic 2.0，商用要另談。

### Opik：Apache-2.0 全功能自架，實驗對比完整
- 兩條評測路線：Test Suites（自然語言斷言＋LLM judge 判 pass/fail）與 Datasets & Metrics（資料集＋指標）（[文件](https://www.comet.com/docs/opik/evaluation/overview)）。
- 有實驗追蹤、可並排比較版本、標註佇列；Apache-2.0 可自架全平台，這是它相對 Phoenix 的優勢。
- **差距**：沒有凍結／不可變語義；評分以 LLM judge 為主，規則判定不是主路徑。

### Langfuse：生態最大，但定位是「追蹤＋評測」
- 36.8k 星，核心是追蹤、提示詞管理（版本控制）、資料集與實驗，評測支援 LLM-as-judge、code evaluator、人工標註（[倉庫](https://github.com/langfuse/langfuse)）。
- 授權是 MIT＋`ee/` 目錄商業授權，自架可用但企業功能分界要看清楚。
- **差距**：資料集與實驗偏「持續觀測」而非「一次性驗收」；凍結語義未見文件（文件站 403，未能核實細節）。

### Inspect AI：評測框架裡最「工程化」的一個
- 由英國 AI Safety Institute 維護，Task／Dataset／Solver／Scorer 四件套，eval log 會記錄 task 版本、模型等中繼資料（[Log 文件](https://inspect.aisi.org.uk/eval-logs.html)、[Tasks 文件](https://inspect.aisi.org.uk/tasks.html)）。
- **Agent Bridge 可直接接第三方 Agent 框架**（OpenAI Agents SDK、LangChain、Pydantic AI），也能跑 Claude Code／Codex CLI 這類外部 agent（[Agents 文件](https://inspect.aisi.org.uk/agents.html)）。這一塊比我們的「HTTP＋模板」更廣。
- **差距**：純 CLI／Python，沒有平台 UI、沒有實驗管理、沒有 A/B 報告；可重現性靠 log 事後追溯。

### DeepEval：pytest 派的代表
- 以 pytest 方式寫測試，內建大量指標（G-Eval、任務完成度、幻覺等），以 LLM-as-judge 與本地 NLP 模型評分（[倉庫](https://github.com/confident-ai/deepeval)）。
- 平台能力（資料集、實驗、報告）在商業產品 Confident AI，開源庫本身不含 UI。
- **差距**：沒有自架平台、沒有凍結、沒有規則評分為主的路徑；適合工程師在 CI 裡用，不適合「給非工程師看的驗收報告」。

### LangWatch／Future AGI／RagaAI Catalyst：平台型新對手
- LangWatch（5.0k★）主打 Agent 可觀測＋模擬測試＋評測，`npx @langwatch/server` 即可自架（[倉庫](https://github.com/langwatch/langwatch)）。
- Future AGI（2.2k★）把評測、追蹤、模擬、護欄、閘道做成一套，Apache-2.0 自架（[倉庫](https://github.com/future-agi/future-agi)）。
- RagaAI Catalyst（16.2k★）有專案／資料集／評測／追蹤管理與自架儀表板，但已 8 個月未更新（[倉庫](https://github.com/raga-ai-hub/RagaAI-Catalyst)）。
- 三者共同點：功能面比我們寬，但都沒把「可重現的驗收」當賣點。

### Braintrust／MLflow／TruLens：實驗管理的老牌做法
- Braintrust 平台閉源，SDK 與 autoevals 開源；experiment 會記錄參數與 git 資訊，但沒有凍結閘（[文件](https://docs.braintrust.dev/)）。
- MLflow 的 Evaluation Datasets 掛在 experiment 底下，配 LLM judge 與追蹤，自架成熟；但未見不可變約束（[LLM 評測文件](https://mlflow.org/docs/latest/genai/eval-monitor/)、[資料集文件](https://mlflow.org/docs/latest/genai/datasets/)）。
- TruLens 用 `app_version` 標記版本並在排行榜比較，judge 可解釋；同樣沒有凍結（[官網](https://www.trulens.org/)）。

### Evalite／Tolokaforge：兩個小而有啟發的樣本
- Evalite（1.7k★）是「TypeScript 原生、本地優先」的評測工具，基於 Vitest，有終端機 UI、支援追蹤與自訂 scorer，明確標示 experimental（[倉庫](https://github.com/mattpocock/evalite)）。它證明「單機、無雲端」的評測工具是有需求的。
- Tolokaforge（22★，2026 新生）做工具型 Agent 的 harness：多輪 agent/user 迴圈、Docker 沙箱、**確定性評分（JSONPath 斷言、state hash、transcript 規則）**、pass@k、SQLite／Postgres runner（[倉庫](https://github.com/Toloka/tolokaforge)）。它的「確定性評分＋SQLite」和我們的取向最接近，但還沒有平台化。

### 基準類：可作為測試集來源
- AgentBench（3.8k★）、τ-bench／τ²-bench、Terminal-Bench、SWE-bench、WebArena、OSWorld、BFCL、ToolSandbox 都是「固定任務＋固定判定」。
- 對 Daoeval 的價值：**測試集可以從這些基準匯入**，而不是自己造案例；判定腳本可以參考它們的狀態比對思路（τ-bench 比對資料庫狀態、BFCL 比對 AST）。

## 8. 判斷二：真的重了的地方，與替代路徑

以下都是「別人已經做好、我們再做一次不划算」的部分。節省人週是依功能面複雜度粗估，不是實測。

| 能力 | 現成方案 | 建議替代路徑 | 粗估節省 |
|---|---|---|---|
| HTTP 自訂接入（請求模板＋響應映射） | promptfoo HTTP provider（`url／method／headers／body／transformResponse`） | 直接把我們的模板 schema 對齊 promptfoo provider 格式，讓配置可互相匯入／匯出；不自創第九種接入描述語言 | 1–2 人週 |
| 規則斷言引擎 | promptfoo assertions（equals／contains／regex／is-json／contains-json／javascript／latency／cost／assert-set） | 斷言型別命名與語義照抄，內部可自寫求值器（要保留三態語義）；不要另造一套 DSL | 2–4 人週 |
| 批量執行編排（併發／重試／暫停續跑） | promptfoo concurrency、Inspect `eval_set`、Tolokaforge SQLite/Postgres runner | `run／run_task` 只保留「快照綁定＋狀態機＋審計」職責；排程細節改用成熟 runner 或至少照抄其狀態機設計 | 2–3 人週 |
| 追蹤與可觀測 | Langfuse／Phoenix／Laminar（OTel） | 不自建 trace 儲存與檢視；以 OTel 上報，Daoeval 只保存實驗與報告 | 4+ 人週 |
| 資料集與實驗對比 UI | Phoenix／Opik／Langfuse | 若要做同等規模的資料集管理與圖表，成本高；建議縮到「凍結視圖＋A/B 對比＋下鑽」，其餘交給外部平台 | 4–8 人週 |
| LLM-as-judge | DeepEval／MLflow／Opik／autoevals | 目前產品明確不做 AI 評分，這是定位選擇；若日後要補，直接接現成 judge 庫，不自研 judge prompt 體系 | 2–3 人週（若要做） |
| 測試集內容 | AgentBench／τ²-bench／SWE-bench／BFCL 等 | 提供「從基準匯入測試集」的轉換器，比自己編案例更有說服力 | 不可估（內容成本） |

**一句話**：執行、斷言、追蹤、資料集 UI 這四塊，用現成的能省掉大半；我們真正該自己寫的，只有「凍結層」和「報告層」。

## 9. 判斷三：獨有或做得更細的地方（逐條判定）

| 機制 | 別人有沒有等價物 | 判定 |
|---|---|---|
| 實驗啟動前凍結四元組（測試集版本＋規則集版本＋重複次數 N＋各分支 Agent 版本），缺一不得啟動 | 最接近的是 Phoenix「versioned datasets＋experiments」與 MLflow「experiment＋dataset」；Inspect 會把 task 版本寫進 log。但都是事後記錄，沒有「啟動閘」 | **真差異（機制層）**，但概念不新；別人靠 git＋設定也能逼近 |
| 啟動時連案例內容、閾值、評分規則一起快照 | 未見任何項目把「案例內容本體」快照進實驗；多數只存引用與參數 | **真差異**，且是最實在的一條 |
| 版本 append-only、只能停用、DB 觸發器強制 | 提示詞／資料集版本化很普遍（Langfuse prompts、Phoenix datasets、MLflow registry），但「不可改不可刪＋資料庫強制」未見公開說明 | **真差異（工程紀律）**；壁壘低，別人補一個 migration 就有 |
| 三態證據 present／none／unavailable | promptfoo 區分 fail 與 error；多數平台用 null／skip 表示缺值。把「取不到」與「明確為空」分開的少 | **部分差異**：資料模型層面不稀奇，統計語義層面少見 |
| N/A 六類原因碼＋報告頂部按原因匯總 | 未見等價實作 | **真差異（呈現層）**，但複製成本低 |
| N/A 不進分母、不當 0 分 | 多數平台計算平均值時本來就忽略 null，效果相近；只是沒有明說 | **叫法不同／實作相近**，別當成賣點 |
| 規則評分（非 LLM judge） | promptfoo 以規則斷言為主；Inspect、Tolokaforge 也是規則優先 | **不是差異**，是同行做法 |
| Wilson 95% 信賴區間＋A/B 改善／退步 | 未見同類產品在 UI 直接給信賴區間；Braintrust／Opik 給平均與並排比較 | **少見**，技術含量低但體驗差異明顯 |
| 匯出 JSON／HTML／PDF 與頁面同設計 token | promptfoo 有可分享的 Web 報告、各家多有 JSON／CSV 匯出；「匯出件與頁面同一套設計 token」未見 | **打磨，不是壁壘** |
| 單機自架、SQLite、無登入無多租戶 | 自架方案不少，但多要 Docker＋ClickHouse／Postgres；我們更輕 | **定位差異（輕量）**，不是功能差異 |

**結論（敢下判斷）**：真正的差異只有兩條半——「啟動前凍結的審計語義」、「append-only 不可變」、「N/A 的統計紀律」。其餘是打磨、叫法不同、或同行共識。護城河不深：Phoenix 離「凍結」只差一個 UI 開關，promptfoo 要加資料集版本也只是時間問題。所以差異化的重點不在功能清單，而在**定位**：把 Daoeval 講成「Agent 上線前的可審計驗收」，而不是「又一個評測平台」。

## 10. 對 Daoeval 的建議

1. **定位收窄**：不做通用評測平台（打不過 Langfuse／Opik 的功能寬度），做「Agent 上線前的可審計驗收」。一句話：*同一份測試集、同一套規則、同一個版本，每次實驗都能證明。*
2. **停止自研**：trace 儲存、LLM judge、通用斷言求值細節、完整資料集管理 UI。這四塊用現成的或直接砍。
3. **加固差異**：凍結四元組的「不可啟動」體驗（缺一就紅字擋住）、快照內容本體、append-only 的視覺化（版本 diff）、N/A 原因碼的報告版面。這四條要寫進產品首頁，而不是埋在詳情頁。
4. **對齊生態**：接入配置對齊 promptfoo provider schema，提供「從 promptfoo 設定匯入」；測試集提供「從 AgentBench／BFCL 匯入」。這是低成本獲客與可信度來源。
5. **補一個短板**：沒有 LLM judge 在「開放式回答」場景會被質疑。建議不是自研，而是以插件形式接 DeepEval／Opik 的 judge，並在報告裡明確標示「規則評分／AI 評分」兩種來源，維持可審計性。

| 保留自研 | `src/server/adapter.ts`（`callAgent`、`mapConversationJson`、`toEvidence`） | 保留請求模板＋響應映射；schema 對齊 promptfoo（見 13.2） | 接入層是產品入口，不能外包 |
| 保留自研 | `src/server/runner.ts`（`startRun`／`pauseRun`／`resumeRun`／`cancelRun`、狀態落庫） | 只留狀態機、進度與續跑語義；併發、重試、限流細節可外借成熟 runner 的設計 | 續跑與審計要自己控 |
| 保留自研 | `src/server/routes.ts` 的實驗端點、`web/src` 的凍結配置視圖與報告頁 | 凍結配置唯讀視圖、缺件紅字擋啟動、報告下鑽 | 這是產品門面，也是「缺一不得啟動」兌現的地方 |

| 砍掉 | `web/src` 測試集頁的通用瀏覽器能力：多條件篩選、標註、人工編輯佇列、跨庫檢索 | 不做；只保留四件事——導入（Excel／CSV）、列表、改草稿、發布版本 | 「帶版本、發布即不可改」的測試集是四元組閘門的一半，這部分反而要加強，不能砍 |
| 砍掉 | 自研 LLM judge 引擎與 judge prompt 體系 | 本輪不建目錄、不寫 judge prompt；需要時以插件接 | 避免規則分與 AI 分混成一個數 |
| 砍掉 | 自建 trace 儲存（新增 span 表、事件表） | 不新增 schema；trace 只作為 `NormalizedTrial.trace` 的證據欄位存在 | 儲存與檢視是兩件事，只留前者 |
| 接外部 | OTel 上報層（`src/server` 新增可選 exporter） | 送往 Langfuse／Phoenix／Laminar；Daoeval 只保存實驗與報告 | 不自建檢視器 |
| 接外部 | judge 插件（DeepEval／Opik／autoevals） | 以插件形式接入，報告標明來源 | 見 13.3 |

| 接外部 | promptfoo provider 設定互導（`src/server/adapter.ts` 內兩個純函式） | 見 13.2，不引入 promptfoo 依賴 | 低成本獲客與遷移路徑 |

**保留的證據欄位不是 trace**：`NormalizedTrial` 的 `rawSnippet`、`httpStatus`、`latencyMs`、`tokenUsage`、`toolCalls`（Evidence）、`error` 全部留在 `store.ts`，供規則評分與報告引用；它們是評分依據，不進 trace 檢視器。

### 13.2 配置互導：promptfoo provider ↔ `AgentConfig`

promptfoo HTTP provider 的 `config` 欄位（`url`／`method`／`headers`／`body`／`transformRequest`／`transformResponse`／`sessionId`／`maxRetries`）與我們的 `AgentConfig`（`src/shared/types.ts`）對照如下。實作放 `src/server/adapter.ts`，寫成 `toPromptfooProvider()` 與 `fromPromptfooProvider()` 兩個純函式，只做映射與校驗，不引入 promptfoo 依賴。

| promptfoo 欄位 | `AgentConfig` 對應 | 關係 | 備註 |
|---|---|---|---|
| `id`（URL 或別名） | `endpoint`＋`name` | 部分 | `id` 是 URL 時等於 `endpoint`；是別名時等於 `name` |
| `config.url` | `endpoint` | 一一對應 | 匯入時若 `url` 含模板變數，記「需人工確認」 |
| `config.method` | `requestTemplate.method` | 部分 | 我們只收 `POST`／`GET`；`PUT`／`PATCH`／`HEAD` 匯入時報錯 |
| `config.headers` | `requestTemplate.headers` | 一一對應 | header 值可含佔位符 |
| `config.body` | `requestTemplate.body` | 一一對應 | `{{prompt}}` → `{{input}}`；其餘變數（`{{caseName}}`、`{{sessionId}}`）保留原名 |
| `config.transformResponse` | `responseMap.outputPath` | 語義對應、語法不同 | promptfoo 接受路徑與 JS 表達式；我們只收固定路徑。匯入時只接受可靜態解析的路徑，其餘標「需人工確認」 |
| `config.transformRequest` | 無 | 我們沒有 | 若日後需要，加 `bodyTransform` 鉤子，不塞進 `AgentConfig` |
| `config.maxRetries` | 無（重試在 `runner.ts`） | 不對應 | 留在 runner 層，不進 `AgentConfig` |
| `config.sessionId` | `requestTemplate.body` 的 `{{sessionId}}`＋會話式適配 | 部分 | Oumi 會話模式自帶 session，語義相近 |
| multipart／文件上傳 | 無 | 我們不支援 | 匯入時標記該 provider 不支援；遇到此類案例記 N/A（`no_scoring_basis`） |

反向（我們有、promptfoo 沒有）：
- `responseMap.statusPath`／`errorPath`／`toolCallsPath`／`tracePath`／`promptTokensPath`／`completionTokensPath`／`totalTokensPath`：promptfoo 無對應，匯出時丟棄，不假裝能對上。
- `targeting`、`allowWrite`、`versionInfo`：我們獨有，不參與互導。
- `authType`／`authHeader`：映射到 `headers` 的 `Authorization`；反向匯入時按 header 名推斷，推斷不出就標「需人工確認」。

互導只覆蓋 provider 層，不覆蓋實驗、評分規則與報告；**單向匯入優先（promptfoo → Daoeval）**，反向匯出作為加分項。

### 13.3 LLM judge：以插件補，不自研（本輪不做）

- 插件介面建議：`judge(input) → { score, rationale, model, promptVersion }`，未來放 `src/server/judge/`（新增目錄），預設關閉。
- 報告每條評分必須帶 `source: 'rule' | 'judge'`；聚合時分開列，**不合成一個數**。
- 開啟 judge 時，`model` 與 `promptVersion` 必須進凍結快照，否則等於自己破壞四元組。
